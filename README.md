# Restaurant Management

## Description
A Java/Spring application for managing a restaurant:
menu items, staff members, tables, orders, customers and bills.


## Technologies
- Java 25
- Spring
- Thymeleaf 
- JSON files


## Project structure
- `model` – entities (Staff, Server, Chef, MenuItem, Bill, Customer, Order, Table, OrderLine, OrderAssignment)
- `repository` – in-memory storage 
- `service` – business logic and validation
- `controller` – web controllers that handle HTTP requests and select the view
- `src/main/resources/templates` – Thymeleaf templates (one folder per entity)


## SOLID principles
- **Single Responsibility:** each layer has one job. Repositories only store data,
  services only validate and apply business rules, and controllers only handle
  interaction with the user. A change in one concern touches only one class.

-**Open/Closed**: The CRUD logic lives in the generic `InMemoryRepository<T>` and `InFileRepository<T>`,
which are closed for modification. Supporting a new entity only requires instantiating them with a new type,
without changing any existing code.


## Architecture
The project uses a layered architecture. Each layer only depends on the one below it:
controller -> service -> repository -> model

- **model** has no dependencies on other layers.
  Chef and Server extend Staff, so a single repository handles all staff members.
  
- **repository** only stores data. A generic `IRepository<T>` interface and an
  abstract `InMemoryRepository<T>`/ `InFileRepository<T>` base class implement the CRUD logic once
  (`save`, `findById`, `findAll`, `delete`), so it is not repeated for each
  entity. Some repositories add their own methods (
  `TableRepository.findByNumber`).
  
- **service** holds all validation and business rules, so they apply no matter
  how the data is accessed. Services depend on the concrete repository classes
  (`ChefService` -> `ChefRepository`).
  
 -**controller** talks only to services, never directly to repositories. Because every repository extends either `InMemoryRepository<T>` or `InFileRepository<T>`, the storage mechanism is encapsulated in a single base class. Switching between in-memory and file storage only requires changing the `extends` clause of the repository classes, and moving to a database only requires replacing that base class. In both cases, the services remain unchanged.

 -**src/main/resources/templates** Thymeleaf templates (one folder per entity)


## Data storage (JSON files)
When the application uses `InFileRepository<T>`, each entity type is persisted
in its own JSON file in the `src/main/resources/data/` folder, one file per entity.

* Each file holds a JSON array with the entities of that type, ten sample
  entities per file, so the application starts with test data.
* The files are read when the application starts and rewritten after every
  create, update or delete, so changes survive a restart.
* `Customer` and `Table` keep their `List<Order> orders`, so their orders appear
  as nested objects in the JSON. Likewise, an `Order` contains its `orderLines`
  and `assignments` as nested lists.
* The sample data mixes `FREE` and `OCCUPIED` tables and `OPEN` and `CLOSED`
  orders, so every state can be seen in the interface.
* IDs are Strings generated by a static counter in each entity's constructor.
  Because the sample IDs are already in the files, make sure the counter starts
  after the highest existing ID, otherwise new entities may get a duplicate ID.


## Web interface (Thymeleaf)
Each entity has its own folder under `src/main/resources/templates/` with three
templates:
* `index.html` – a table listing all entities, with Details, Edit and Delete buttons per row
* `form.html` – a form used both for creating a new entity and for editing an existing one
* `details.html` - a read-only page showing all the fields of a single entity,
  with a link back to the list

  
### How a request is handled
1. **Listing:** the browser sends `GET /<entity>`. The controller puts the list
   into the `Model` (`model.addAttribute("orders", ...)`) and returns the
   template name (`"order/index"`). Thymeleaf renders the HTML, iterating the
   list with `th:each`.
2. **Creating:** `GET /<entity>/new` puts an empty object into the `Model` and
   shows `form.html`. The form is bound to it with `th:object` and `th:field`.
   On submit, the browser sends `POST /<entity>`; Spring creates the object
   from the form values (using the empty constructor and the setters) and passes
   it to the controller, which calls the service.
3. **Viewing details:** `GET /<entity>/details/{id}` reads the `{id}` with
   `@PathVariable`, loads the object through the service, puts it into the
   `Model` and shows `details.html`, which displays the fields with `th:text`.
4. **Editing:** `GET /<entity>/edit/{id}` loads the existing object and shows
   the same `form.html`, now pre-filled with its values. On submit, the browser
   sends `POST /<entity>/edit`; Spring binds the form values to the object
   (`@ModelAttribute`) and the controller passes it to the service's `update` method.
5. **Deleting:** the Delete button submits a form with `POST /<entity>/{id}/delete`.
   The `{id}` is read in the controller with `@PathVariable`.
6. After every POST the controller returns `redirect:/<entity>`
   (Post/Redirect/Get). The browser then requests the list again, so the page
   always shows the current data and a refresh does not resubmit the form.



### Available pages
The application runs on `http://localhost:8080`.


| Entity    | List          | New               | Details                     | Edit                     |
|-----------|---------------|-------------------|-----------------------------|--------------------------|
| Customer  | `/customer`   | `/customer/new`   | `/customer/details/{id}`    | `/customer/edit/{id}`    |
| Table     | `/table`      | `/table/new`      | `/table/details/{id}`       | `/table/edit/{id}`       |
| Menu item | `/menuItem`   | `/menuItem/new`   | `/menuItem/details/{id}`    | `/menuItem/edit/{id}`    |
| Chef      | `/chef`       | `/chef/new`       | `/chef/details/{id}`        | `/chef/edit/{id}`        |
| Server    | `/server`     | `/server/new`     | `/server/details/{id}`      | `/server/edit/{id}`      |
| Order     | `/order`      | `/order/new`      | `/order/details/{id}`       | `/order/edit/{id}`       |
| Bill      | `/bill`       | `/bill/new`       | `/bill/details/{id}`        | `/bill/edit/{id}`        |

`{id}` is the ID of the entity, as shown in the list. The Details and Edit
pages are normally reached through the buttons in each row of the list, not by
typing the URL.

Create entities in this order: customer and table first, then the order (using
the customer ID and table ID shown in the lists), then the bill (using the order
ID).


## How to run
1. Clone the repo
2. Open it in IntelliJ
3. Run the `RestaurantManagementAppApplication`
4. Open `http://localhost:8080/customer` (or any other page from the table above)
